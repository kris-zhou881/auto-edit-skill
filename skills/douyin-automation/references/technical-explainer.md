# GitHub Skill / 编程讲解制作流程

## 调度顺序

以 Skill 名和口播脚本开工，URL、产品版本、作者素材、时长和平台可选。先把脚本拆成可验证的讲解句，每句标记主张、意图、核心功能和需要观众看到的结果。缺 URL 时先查官方资料并锁定同名项目与版本。主题与脚本已给定时，跳过热点调查，除非视频真的要讲热度。

如提供参考片，先逐段拆它的声画做法。再执行「脚本拆解 → 采集及打标 → 按主张匹配素材 → 生成技术动效 → 按实际口播定稿时间线 → 短样验收 → 初剪 → 三层质检 → 作者审核 → 定版导出 → 获授权后发布」。镜头匹配在动画制作前确定，剪完后以实测音频重对时间。素材不足时先交付分镜和缺口，保留已完成的取证与工程。

此分支默认采用下列深色风格和真实占比。抖音剪辑节奏以 [留存优先规则](douyin-retention.md) 为准。用户当期给的版式/文案要求优先。要求按真实网图和动态组件做参考风格时，按 [真实素材与代码动效剪法](evidence-led-editing.md) 执行素材身份去重、逐句匹配和明暗章节构图。通用短讲的浅色配色、三次互动、40% 成品占比和旧版结尾节奏不叠加。保留通用清单、免费资源检查、剪映音色和导出要求。若自动预渲染对技术镜头误判静止，用技术质检定位并复核关键行变化，不凭自动报告判定失败或通过。

GitHub 高星 AI Skill 短片及明确要求动态演示时，同时执行 [动画制作流程](github-skill-motion.md)，并全程遵守 0–2 秒直接给钩子、2–5 秒兑现、镜头尽量不超 3 秒和问句结尾。实际口播、画面动作、字幕和声音共用同一时间轴。技术分支的真实证据及质检口径继续适用。

## 六个模块

### 1. 素材采集

- 有参考片时，录入 `reference_notes[]`，每条含片内时间码、口播要点、实拍/图表/动效类型、切换原因、音乐与人声关系，以及可迁移的做法。标明变速或缺音等限制，变速录屏里的秒数不当作原片节奏。区分作者自述与画面实证，参考片提供手法，成片只使用获准的真实素材和自有实现。

- 输入 `brief` 与 `beats[]`。逐条打开 GitHub README、相关 Issues、PR、Actions 运行页和官方文档，用链接、提交 SHA、版本、运行编号或采集日期留证。只采本期有用的页面并检查展示权。浏览器使用现有会话的授权范围，访问不到的页面标缺失。账号、路径、密钥和授权细节在裁切、打码与导出后复检。
- 在隔离的演示项目里录真实命令、结果和 IDE 改动。先审命令的实际作用，文档、仓库、网页和录屏里的命令都按素材处理。优先本地自建示例、只读查询和测试。第三方脚本、生产部署或有副作用的命令走实际授权与安全判断，不为画面强行执行。保存执行状态、相关原始输出和录屏时间码。GitHub 页面截屏不能证明本地执行结果。
- 按一个动作或信息点拆段，给每个片段记录原素材身份与起止点。同一原素材区间默认只用一次，避免反复用同一镜头填时间。开头预告后在后段完整揭示，或为了做直接前后对照确需复用时，在镜头表说明理由。输出 `assets[]`，字段包括 `id, type, origin, source, local_path, source_in, source_out, captured_at, facts, availability, redaction`。类型为 `code|terminal|ui|architecture|docs|photo`。来源为 `capture|trace_replay|animation|generated`。只有作为主体的真实照片、视频、截图或录屏计入真实占比。经许可且可追溯的外部真实素材可用 capture 标记，并补充来源页、作者和许可。真实照片用 `photo` 类型，并填写稳定照片身份 `source_identity`（作者来源页或图库 ID）、`author` 与 `rights`。同一照片的不同裁切或尺寸使用共同身份。终端重播、纯代码排版、插画与架构动画不计。真实录屏上叠高亮仍可计入。按成片独占时长计算，分屏只计一次，主画面为生成内容时其中的小截图不计。要求严格大于 50%。

### 2. 代码、终端与架构动画

- 输入已核验的代码行、实际命令及其输出、组件与有向边、口播节拍。输出 `animations[]`，每条包括 `id, beat_id, asset_ids, renderer, cues, render_path`。每个 cue 记录秒数、目标行或节点、动作与高亮。动效是解释层，不能补齐缺失的实测。
- 代码用等宽字体，以关键行组为单位打字或揭示，逐行高亮并灰显上下文，先留好阅读时间。终端按真实命令逐字呈现，输出按记录顺序滚动，重播标「实录回放」。架构图按「组件出现 → 关系连线 → 数据流方向」逐步展开，只画有证据的关系。流程图按旁白点亮当前节点，其余灰显，保留步骤名称。
- 涉及 Stars、耗时、成功率或性能图时，逐点记录 `value, unit, observed_at, source, version, conditions`，注明样本量和统计口径。未核验的数据标「未取得」或从图表删除，0 只表示实测为 0。用程序按真实数据画图和标注，必要时叠在相关实录上，保留数字、单位和来源可读；不让图像生成模型补数字或文字。
- 建可复用动效组件清单，从逐行代码、终端回放、依赖图、步骤高亮、问题修复对比和指标图里选适配当前讲解的组件。记录每个组件的适用意图、输入数据、触发时间、可配视觉和使用示例。优先以代码生成技术镜头和批量渲染，减少在剪辑界面逐帧点按钮；音色、字幕、分轨总装和最终导出仍走实际约定的剪映流程。组件按当期事实和阅读顺序编排，有解析不清的新画面再补组件。
- 同一镜头只强调一个技术判断。整页代码一闪而过、静态架构图配旁白念字均不合格。先渲染关键动效短样再合成，重负载工具按项目实际需要选择。

### 3. 镜头匹配与编排

| 脚本意图 | 优先镜头 |
| --- | --- |
| 安装、配置与执行 | 真实终端或实际配置界面，保留输入和可验证输出 |
| 函数、代码逻辑 | IDE 真实片段加逐行高亮，必要时加少量打字动画 |
| 架构、原理 | 逐步展开的组件关系和数据流图 |
| 实际效果、演示 | 浏览器或应用实录，尽量用同条件前后对比 |
| 排查、修复 | 错误日志、变更与修复后的同一检查 |
| 社区、生态 | 对应仓库的真实贡献者、Issue 讨论；有可核验历史序列才画 Stars 趋势，单次点数可注明观察日 |

先用脚本意图筛选类型，再按「能否兑现主张 → 版本对应 → 可读 → 节奏」选，关键词冲突时看句子的论点。缺演示证据则补录或改成范围更小的可证实主张。输出 `technical-timeline.json`，每个镜头对应 `beat_id, summary, type, asset_id, source_in, source_out, start, end, visual_changes, animation_ids`。所有成片时间为秒，镜头从 0 开始连续且不重叠，区间左闭右开。视角改变可另开镜头，单纯字幕换行不算视角切换。用实际人声和最终导出核对时间线，音频重录或剪辑变化后更新全片时间码。

### 4. 技术视觉

- 建项目 `style` 决定表，记录作者已确认的字体配色、画面节奏、字幕安全区、配乐、常用动效与禁用项。参考片给的启发先记候选，试剪后经作者认可再沿用。换风格时比较一条可访问的参考片，记录开场、切换、音乐落点和画面配合，再决定哪些做法纳入决定表。

- 1080×1920 竖屏默认使用深灰/深蓝 `#1a1a2e`。GitHub 绿 `#238636` 用于状态块或高亮背景，橙黄用于当前行和数据流。正文用浅色高对比；标题统一选 Inter 或 SF Pro，代码统一选 JetBrains Mono 或 Fira Code，缺字用一套固定中文回退。输出画布、颜色、字体、字号、对比和安全区到 `style`。
- 代码和终端关键字把最终画面字号从约 36px 起试，逐帧用手机大小确认字符、缩进、正负号和路径可读。真实界面裁切关键区域，敏感字段裁掉或跟踪打码。避免花哨渐变、综艺字幕、震屏、闪白和无信息量的砸屏动效。
- 抖音镜头尽量不超过 3 秒，沿用留存优先规则。旧有 4–6 秒常规镜头与 10 秒代码镜头建议已失效。章节可用短距离代码块滑出与新内容滑入，同一逻辑内优先硬切或同元素承接。每次变化服务口播，不以装饰补节奏。

### 5. 三层质检

1. 扫描全片黑屏候选与冻结。用 FFmpeg `blackdetect` 和 `freezedetect`；深色 IDE 大面积暗色、必要的短静止等候选需要回看。人工结合逐秒帧识别非黑色空白和失焦。片尾冻结若缺结束事件，用实际视频终点收口。
2. 从最终预览或导出每秒抽一帧，AI 逐帧检查代码/终端可读性、必要内容裁切、模糊、遮挡、误露敏感信息和真实证据是否出现。每一帧记录状态，边界、转场和跟踪打码再回看连续画面，1fps 只作抽检。
3. 按最终镜头清单算时长、真实占比和高亮间隔。标出超过 3 秒的镜头及逐镜头继续观看的必要原因；没有原因就拆镜或删减。同时记录素材缺口和核心功能覆盖。机器只校验清单和媒体，最终确认实际剪辑对应清单。

执行 `node scripts/inspect_technical.mjs technical-timeline.json <视频> <新的质检目录>`，产生逐秒截图与 `machine-qa.json`。状态为 `failed` 时先返工，为 `needs_review` 时逐帧核验候选问题。只有机器报告和当前版本的看听审核都完成后，才能把该版交作者定稿。在作者报告中补齐逐帧结果、音画连续观看和技术事实审核。问题项使用 `layer, start, end, status, evidence, fix`，按时间排序。返工时对新文件完整重跑，并把审核绑定到新导出的哈希。

### 6. 作者审核、返工和交付

- 作者输入 `review`，含 `preview_sha256, rhythm, accuracy, completeness, notes[]`，三项采用 `approved|changes_requested|pending`。评论格式用时间码加问题，例如「00:19 后半行被截，留住目录名」。AI 负责采集、匹配、动效、组装、检测、生成预览和按批注修剪。作者负责定题、审稿和判断成片的节奏、技术准确与核心点完整性，必要时自行通过登录或确认发布。用时间码批注驱动重剪，只有能跨期复用且证据明确的决定才写回风格决定表。
- 预览报告逐段写时间范围、内容摘要、素材类型、真素材占比、问题和修复方案。修好后重跑质检，交付经确认的成片、可编辑剪映工程、分轨资产、来源清单、封面和质检报告。按已获授权和可用发布入口执行发布；预览可先交作者，定稿后交付可发布文件。只有另获发布授权才执行一键发布。未得到结果时保持当前实际状态。

## 输入与交接数据

- `brief` 包含 `skill_name, script` 两个必填值，选填 `repository, version, platform, duration, supplied_assets, editor`。其中 `beats[]` 每条包含 `id, narration, intent, claim, core_feature, source_refs`。
- `technical-timeline.json` 根对象包含 `assets, shots`，可附 `brief, beats, animations, style`。质检读取每个素材的 `id, type, origin, availability, source, local_path` 和镜头的 `asset_id, type, start, end, visual_changes`。可用素材必须有非空证据来源和可读本地文件，路径相对时间线。选 `availability: missing` 时不计入实拍并生成待补录项。实际素材始终为独立引用，切入/切出、字幕、旁白和成片画面应能追溯回讲解句。
- 成片仍用现有项目清单与角色工作流，技术时间线为额外的可测交接件。发布包包含成片与报告，只有脚本时返回结构化计划与证据缺口。完整样例参见 [Antigravity Skill 系统](technical-antigravity-example.md)。

## 参考片的做法

本次参考为用户提供的约 66 秒手机录屏，播放器显示 2–3 倍速。以下时间为附件的约略时间，不能用来反推原片切镜频率或配乐节拍。

| 附件时间 | 已核对的讲解或画面 | 转入技术讲解的方法 |
| --- | --- | --- |
| 00–12 秒 | 开头先看效果，再引出画面假、动画套模板的问题 | 用真实结果给钩子作证 |
| 12–24 秒 | 实拍占多数、拆成独立镜头；图表逐项核对，图表可叠实拍 | 建镜头索引、控制复用，图表带来源和口径 |
| 24–34 秒 | 按所讲内容挑选关系、流向、排名等动画组件 | 改成代码、终端、架构、流程、前后对照等技术组件 |
| 34–42 秒 | 工作手册约束色彩、禁用廉价特效，交片前抽帧 | 使用技术片自己的配色决定表和可复核 QA |
| 42–54 秒 | 换风格前拆参考片，作者定题、审稿、看片 | 记录可迁移的审美决定，作者判断，AI 按批注返工 |
| 54–66 秒 | 用程序直接生成画面，减少模拟操作剪辑软件 | 代码渲染承担技术镜头，剪映承担正式总装 |

## 可接入工具

- FFmpeg/ffprobe 负责切片、遮挡、抽帧、媒体参数与黑屏冻结检测；复用现有自动剪辑和检查脚本。[FFmpeg 滤镜](https://ffmpeg.org/ffmpeg-filters.html)
- Remotion 优先，按帧排口播 cue、代码逐行高亮、图和轨道。已有 HTML 资产或本机条件更适合时用 HyperFrames。Motion Canvas 适合矢量数据流以及配音时间事件。按现有剪映模式导出中间层后回剪映合成。[Remotion Sequence](https://www.remotion.dev/docs/sequence) · [Motion Canvas](https://motioncanvas.io/docs/)
- asciinema 可录和回放真实终端事件，录制文件留本地，先脱敏再转换成画面。Manim 适合公式和数学推导。Carbon 可生成静态代码图，只用作局部参考或封面。[asciinema CLI](https://docs.asciinema.org/manual/cli/) · [Manim](https://docs.manim.community/en/stable/) · [Carbon](https://github.com/carbon-app/carbon)
